# Architecture

## Overview

```
┌─────────────┐      JWT (Bearer)      ┌──────────────┐
│  Next.js    │ ─────────────────────▶ │   FastAPI    │
│  (apps/web) │ ◀───────────────────── │  (apps/api)  │
└─────────────┘        JSON            └──────┬───────┘
                                               │
                          ┌────────────────────┼────────────────────┐
                          ▼                    ▼                    ▼
                    ┌───────────┐       ┌─────────────┐     ┌──────────────┐
                    │ Postgres  │       │    Redis    │     │ OpenAI /     │
                    │ (SQLAlchemy│      │ (Celery     │     │ Anthropic /  │
                    │ + Alembic)│       │  broker)    │     │ Gemini (REST)│
                    └───────────┘       └──────┬──────┘
                                               ▼
                                        ┌──────────────┐
                                        │ Celery worker │
                                        │ + beat        │
                                        └──────────────┘
```

The frontend is a client-rendered SPA-style app: pages fetch directly from the
FastAPI backend using a JWT stored in `localStorage`, with a fetch wrapper
(`apps/web/lib/api-client.ts`) that transparently refreshes the access token on
a 401. This sidesteps Next.js's server-side caching model entirely — nothing
here needs `"use cache"` or server actions, since all state lives in Postgres
behind the API, not in React Server Components.

## Backend structure (`apps/api/app/`)

- `models/` — SQLAlchemy ORM models, one file per entity. `models/base.py`
  provides a UUID primary key + timestamp mixin every model inherits.
- `schemas/` — Pydantic request/response models, kept separate from ORM models
  so the API contract can evolve independently of the database schema.
- `api/v1/` — one router per resource, thin: auth/ownership checks and
  delegation to `services/`, no business logic embedded in route handlers.
- `services/` — business logic. Notably:
  - `services/ai/` — the `AIProvider` strategy interface plus one
    implementation per provider (OpenAI, Anthropic, Gemini), each a direct
    REST client via `httpx` (no SDK dependency, no vendor lock-in in the
    abstraction).
  - `services/agents/` — the 12 AI agent personas (`personas.py`) and the
    runner that optionally grounds a persona's prompt with real Postgres data
    before calling the provider (`runner.py`).
  - `services/scheduler_service.py` — publishes due posts via the
    `Publisher` interface.
  - `services/dashboard_service.py` — aggregates `Metric` rows into the
    dashboard payload, including the linear-regression growth projection.
- `integrations/` — the extension point for real social-platform publishing.
  `base.py` defines the `Publisher` ABC; `log_publisher.py` is the honest
  default (marks a post published and logs it, no external calls); a real
  platform integration is a new `Publisher` subclass registered in
  `registry.py` — nothing else in the scheduling pipeline changes.
- `workers/tasks.py` + `celery_app.py` — Celery task definitions and the beat
  schedule (publish-due-posts every 60s; daily/weekly/monthly summaries on
  cron).
- `middleware/` — rate limiting (slowapi) and an audit-log middleware that
  records every mutating request.
- `deps.py` — `get_current_user` (JWT decode) and `require_roles(...)` (RBAC
  dependency factory).

## Frontend structure (`apps/web/`)

- `app/(dashboard)/` — route group for every authenticated page, sharing the
  sidebar/topbar layout (`app/(dashboard)/layout.tsx`), which also handles the
  redirect-to-login guard.
- `components/ui/` — a small shadcn-style component kit built directly on
  Radix primitives (no external shadcn CLI dependency, so there's nothing to
  drift out of sync).
- `components/{crm,calendar,content,dashboard,layout}/` — feature components,
  one directory per feature area.
- `lib/api-client.ts` — the only place that talks to `fetch`; every page goes
  through `api.get/post/patch/delete`.
- `lib/auth-context.tsx` — React context holding the current user and
  login/register/logout, backed by the API client.

## Data model

See the Alembic migration at `apps/api/alembic/versions/` (autogenerated from
the models, so it's guaranteed to match) for the full schema. Thirteen tables:
`users`, `leads`, `deals`, `pipeline_stages`, `tasks`, `notes`, `posts`,
`notifications`, `audit_logs`, `social_accounts`, `metrics`, `ai_generations`,
plus `alembic_version`.

## Why linear regression, not "AI", for growth projections

The dashboard's 30-day projection is an ordinary-least-squares fit over recent
daily metric history (`services/dashboard_service.py::_linear_projection`),
returned with its R² as a `confidence` field and a `method` field that always
says `linear_regression_7d`. It's intentionally not dressed up as a machine-
learned forecast — that would need a real model, real training data, and real
backtesting, none of which exist yet. The API is honest about what it is.
